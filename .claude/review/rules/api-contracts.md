# API Contracts — Focus Areas

MPDX talks to two GraphQL servers through one Apollo Client, and owns the second one itself. Both
contracts are enforced by code generation against a **live** schema, so a contract break shows up as
a red CI build for the whole team — or, worse, as an operation silently routed to the wrong server.

**Trigger this review when the diff touches** any `.graphql` file, `pages/api/Schema/**`,
`pages/api/graphql-rest.page.ts`, `src/lib/apollo/link.ts`, `codegen.ts`, or adds/renames fields in an
operation.

---

**The routing contract — `src/lib/apollo/link.ts` + `src/graphql/rootFields.generated.ts`**

- `rootFields.generated.ts` is generated by `./extractRootFields.js` from the **native API schema
  only** (`codegen.ts` passes `schema: apiUrl` there, deliberately excluding the REST-proxy schema).
  It is the authoritative list of which root fields the native API owns.
- `isNativeOperation(operation)` returns true only when **every** top-level selection of **every**
  operation definition is in that set. `batchLink` then routes the entire document to one server.
- **Therefore:** one REST-proxy-only field in an otherwise-native operation sends every field to
  `/api/graphql-rest`, which does not define them, and the query fails. This is the single most
  common contract bug in this repo.
- Look for: a field added to an existing operation without confirming which server owns it; a new
  operation that mixes e.g. `contacts` with `reportsStaffExpenses`; someone modifying
  `isNativeOperation` to attempt per-field splitting.
- Native traffic goes to `process.env.API_URL`; both native and proxy traffic default to
  `BatchHttpLink` (`batchMax: 25`, `batchDebounce: true`, `batchInterval: 20`). The native side has an
  unbatched `createHttpLink` escape hatch selected by `context: { doNotBatch: true }`.
  The proxy server sets `allowBatchedHttpRequests: true` to match — don't disable it.

**The codegen contract — `codegen.ts` / `yarn gql`**

`yarn gql` reads `schema = [apiUrl, './pages/api/Schema/**/*.graphql']` and writes:

| Output                                           | Purpose                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------- |
| `src/graphql/types.generated.ts`                 | shared scalars/enums/input types                                    |
| `src/graphql/schema.graphql`                     | the merged SDL — used by `GqlMockedProvider` in tests               |
| `src/graphql/possibleTypes.generated.ts`         | fragment matcher for `InMemoryCache`                                |
| `<operation>.generated.ts` (near-operation-file) | typed hooks + operation types                                       |
| `pages/api/graphql-rest.page.generated.ts`       | `Resolvers` typed with `contextType: './graphql-rest.page#Context'` |
| `src/graphql/rootFields.generated.ts`            | the routing table above                                             |

- `afterAllFileWrite` runs `prettier --write` then `node deleteStaleFiles.mjs`, which removes
  generated files whose source `.graphql` is gone. A PR that deletes a `.graphql` but leaves a stale
  `.generated.ts` import behind will fail `yarn lint:ts`.
- All of `src/graphql/` and every `*.generated.ts` is **gitignored** — never review them as source,
  never commit them (the one deliberate exception is `pages/api/auth/apiOauthSignIn.ts`, hand-written
  in generated style because the field is staging-only).
- Look for: a `.graphql` change with no evidence `yarn gql` was run; a hand-written type that
  duplicates a generated one; a generated file accidentally committed.

**Breaking changes against a live production schema**

`codegen.ts` defaults `API_URL` to `https://api.stage.mpdx.org/graphql`, but CI pins it:

```
API_URL: contains(labels, 'Staging API') && 'https://api.stage.mpdx.org/graphql' || 'https://api.mpdx.org/graphql'
```

- So codegen normally validates every operation against **production**. If a field this PR selects is
  not on production yet, `yarn gql` fails in the `test`, `eslint`, `typescript`, and
  `bundle-analyzer` jobs.
- The escape hatch is the **"Staging API" PR label**: it switches codegen to staging _and_ enables the
  `staging-api-block` job, which unconditionally `exit 1`s. The label means **"this operation is not
  on production yet — do not merge."**
- Reviewer duties when the label is present: confirm the API-side change is merged/deployed to
  production before this PR merges, that a ticket tracks it, and that the label is removed (not the
  `staging-api-block` job).
- Look for: removing or weakening `staging-api-block`; setting `API_URL` to staging outside the label
  condition; renaming a field the upstream API still serves under the old name.

**The REST-proxy contract — `pages/api/Schema/<Feature>/`**

Adding a proxied query or mutation means all five of:

1. **Schema** — `<feature>.graphql` using `extend type Query` / `extend type Mutation` plus its input
   and payload types. The proxy is built with `@apollo/subgraph`'s `buildSubgraphSchema`, so `extend`
   is required, not optional.
2. **Resolver** — `resolvers.ts` exporting a `Resolvers`-typed object from
   `pages/api/graphql-rest.page.generated`, whose body only destructures arguments and calls
   `dataSources.mpdxRestApi.<method>(...)`. No transformation here.
3. **REST method** — an `async` method on `class MpdxRestApi extends RESTDataSource` in
   `pages/api/graphql-rest.page.ts` using `this.get/post/put/delete` against
   `process.env.REST_API_URL`.
4. **Data handler** — a sibling file mapping the REST/JSON:API response onto the generated payload
   type.
5. **Registration** — an entry in the `buildSubgraphSchema([...])` array in `pages/api/Schema/index.ts`.

`pages/api/Schema/Contacts/DonorAccounts/Destroy/` is the minimal complete example
(`destroyDonorAccount.graphql` → `resolvers.ts` → `MpdxRestApi.destroyDonorAccount` →
`datahander.ts`).

- **A `.graphql` file that is never registered in `index.ts` silently does not exist** — the field
  isn't in the schema, `yarn gql` won't emit it, and the operation fails at runtime. Flag every new
  schema file without a matching `index.ts` import + array entry.
- Handler filenames are already inconsistent in-tree (`datahandler.ts`, `dataHandler.ts`, and one
  `datahander.ts` typo). Match the nearest sibling.

**snake_case → camelCase mapping is where fields go missing**

- `src/lib/snakeToCamel.ts` exports `snakeToCamel`, `camelToSnake`, `camelToSnakeObject`;
  `pages/api/graphql-rest.page.ts` also defines a local `camelToSnake` at the top of the file. Don't
  add a third copy.
- `src/lib/deserializeJsonApi.ts` `fetchAllData(object, includedData)` recursively resolves JSON:API
  `relationships` against `included`, camelCases every attribute key, and attaches `id`. It is
  untyped, and its results are cast (`as FinancialAccountEntry[]`) — a renamed upstream field
  disappears with **no type error**.
- Look for: a field present in the hand-written `*Rest` interface but absent from the returned object;
  `data?.foo` where the payload nests under `attributes`; a `Object.keys(meta).forEach` loop that
  drops a key (`financialAccountEntriesHandler` drops `pagination` deliberately — keep that comment);
  numbers left as strings.

**Error-code contract between proxy and client**

`MpdxRestApi.errorFromResponse()` does two contractual things:

- copies `parsedBody.errors[0].detail` into `error.message` (that string reaches the user's snackbar)
- maps a REST `errors[0].status === '404'` to `error.extensions.code = 'NOT_FOUND'`, **because**
  `src/lib/apollo/accountListRedirect.ts` + `src/lib/apollo/client.ts` use it to detect an
  account-list-not-found error and redirect to the user's default account list

The client separately treats `extensions.code === 'AUTHENTICATION_ERROR'` as a forced sign-out.
Changing or removing either mapping silently breaks a user-visible flow.

`parseBody()` is overridden to accept `application/vnd.api+json` and `application/hal+json`, and to
return text for `204`/`Content-Length: 0` rather than throwing on `JSON.parse`. Preserve those cases.

**Scalars**

- `pages/api/Schema/scalars.graphql` declares `ISO8601Date` and `ISO8601DateTime`;
  `pages/api/Schema/scalarResolvers.ts` registers them as bare `GraphQLScalarType`s with **no**
  `serialize`/`parseValue`/`parseLiteral` — identity pass-throughs.
- `codegen.ts` maps both to TypeScript `string` (and `PositiveFloat` to `number`) in
  `types.generated.ts`.
- Consequence: dates are strings on both sides of the boundary. A data handler must not hand back a
  `Date` or a Luxon `DateTime`.
- A new scalar means: declare it in `scalars.graphql`, register it in `ScalarResolvers`, **and** add
  it to the `scalars` map in every relevant `codegen.ts` output, or it types as `any`.

**Auth at the boundary**

The proxy's Apollo Server context constructs `new MpdxRestApi(req.headers.authorization ?? '')` per
request, and `willSendRequest` forwards that header plus `Content-Type: application/vnd.api+json`.
There is no service account. See rules/security.md.

### API Contract Checklist

- Operation routes cleanly to one server (checked against `rootFields.generated.ts`): Yes/No/N/A
- `yarn gql` run and succeeding; no generated files committed: Yes/No/N/A
- New/renamed fields exist on the **production** API, or the PR carries the "Staging API" label with a tracked deploy: Yes/No/N/A
- New proxy feature has all five pieces (schema, resolver, REST method, data handler, `index.ts` registration): Yes/No/N/A
- Resolver contains no transformation logic: Yes/No/N/A
- Every REST field is mapped or explicitly and visibly ignored: Yes/No/N/A
- String-typed REST numbers converted; dates left as ISO strings: Yes/No/N/A
- `NOT_FOUND` / `AUTHENTICATION_ERROR` error-code mappings preserved: Yes/No/N/A
- New scalars declared, resolved, and added to the codegen scalar maps: Yes/No/N/A

## Mined from merged PR history

Rules derived from 50 merged PRs (#2002–#2056). Each carries the PRs it came from.

- **Cross-repo deploy order — the single most frequent theme in this repo's history (15 of 50 PRs).**
  A PR whose GraphQL documents reference a field, enum member, or input type not yet live on
  production must name the paired `CruGlobal/mpdx_api` PR in its body, state which side ships first
  and why, and carry the `Staging API` label. The mechanics that make this load-bearing:
  `src/graphql` is gitignored, `ci.yml` codegens against `https://api.mpdx.org/graphql` unless the
  label is present (then `api.stage.mpdx.org`), and the label itself has a `staging-api-block` job
  that fails to prevent merge. So a red codegen or `lint:ts` check on such a PR is a deploy-ordering
  fact rather than a defect — but confirm the failure is exactly the missing field before accepting
  it. The two directions differ: a frontend **field removal** must merge and deploy first (the API
  PR drops the field from both the type and the mutation input, so a still-deployed frontend fails
  on reads and every save), while a frontend **addition** must wait for the API to deploy. Flag any
  paired PR that does not say which side ships first.
  <!-- evidence: PR #2017, #2019, #2021, #2022, #2023, #2027, #2028, #2033, #2035, #2037, #2040, #2043, #2048, #2053, #2054 -->
- Selection sets must match what the component actually renders, and a schema change must be swept
  for stale references. Flag fields selected in a `.graphql` document with no production reader
  (`tenure` / `spouseTenure` left selected after both call sites were hardcoded; `accountId` read
  only by test mocks; a selected `printedCount` never used) — either drop it or use it, and note
  that the "always include `id`" rule does not apply to a type with no `id` in the schema (say so in
  a comment rather than adding an unrelated field). When the backend merges two fields into one
  (`additionalSalary` + `reimbursement` → `asrAndReimbursements`), run `yarn gql` and grep for stale
  references **including mock-data generators** — carrying over only one of the two seed terms
  silently shrank a mock's rendered range. Removing the last client-side guard on the premise that a
  backend field is "never populated" requires that field to be deprecated or removed in the paired
  API PR; flag a deletion that leaves it live in `src/graphql/schema.graphql`.
  <!-- evidence: PR #2009, #2038, #2041 -->
